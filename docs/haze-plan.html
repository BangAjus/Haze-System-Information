Architecture & project plan · v0.1 draft

Haze: a city air-quality pipeline, forecast model, and two apps

An end-to-end portfolio project built on the Global Weather & Air Pollution dataset. It covers ingestion, warehousing, data quality, orchestration, a PM2.5 forecast model, one API, a web operations dashboard, and an iOS app for everyday users.

Working name: HazeDrafted 17 Oct 2026Source: Kaggle · xjoannax88 (CC BY 4.0)
01

Overview

The dataset is refreshed daily. Each refresh holds one snapshot of weather and pollutant readings for the three most populous cities in each country, collected from the OpenWeather Current Weather and Air Pollution APIs. Because it keeps growing, it supports a real incremental pipeline rather than a one-off notebook.

The project ships three things that share one warehouse and one API:

Data engineering

Pipeline + ML

Dagster orchestrates ingestion, dbt models, data quality checks, feature building, weekly retraining and daily forecasts. Every run writes its own metadata to the warehouse.

For engineers & analysts

Web ops dashboard

Pipeline health, data quality, freshness and model accuracy, next to a world map and city explorer for the data itself.

For the public

iOS app

Air quality for your city right now, tomorrow's forecast, saved cities, threshold alerts and home-screen widgets.

Design principle

The monitoring view is not an embedded Airflow or Dagster screen. The pipeline records its own runs, checks and model metrics in ops and ml tables, and the dashboard reads them through the API. Dagster's UI stays available through deep links for debugging.

03

Ingestion

Source A: Kaggle (phase 1)

  • A Dagster sensor polls the dataset's metadata through the Kaggle API every 30 minutes. When the version number changes, it launches the daily ingest for that date. This avoids guessing what time the author publishes.
  • Download with kaggle datasets download xjoannax88/global-weather-and-air-pollution-dataset. Write the files to the raw folder as Parquet, then load them into raw.weather_air_snapshots.
  • The file may contain the full history rather than only new rows. Either way, the load upserts on (city_key, observed_at_utc), so rerunning a day is safe.
  • The Kaggle token lives in .env and is passed in through a Dagster resource. It is never committed.

Source B: OpenWeather directly (phase 2)

  • Use the same city list (from core.dim_city) and call the Current Weather and Air Pollution endpoints every hour. This gives 24 readings per city per day instead of one, which helps the forecast model a lot.
  • Several hundred cities times two endpoints per hour adds up quickly. Check the free-tier call limits before turning this on, and keep the request rate low.
  • OpenWeather also has an air pollution history endpoint. It could backfill past PM2.5 readings so the model has more than a few months to learn from.

City key

The dataset has no city ID. Build a stable surrogate key: city_key = md5(country_code || '|' || lower(city_name) || '|' || round(geo_lat, 2) || '|' || round(geo_lon, 2)). Rounding the coordinates keeps the key stable if the source changes them slightly. Two cities with the same name in one country stay separate.

04

Schemas

Timestamps are UTC timestamptz. Pollutant concentrations are µg/m³ as OpenWeather reports them. AQI uses OpenWeather's 1–5 scale. During staging, check what unit the temperature columns use (Kelvin or °C) and store it in °C.

1 · GoodPM2.5 < 10
2 · Fair10–25
3 · Moderate25–50
4 · Poor50–75
5 · Very poor≥ 75

PM2.5 ranges in µg/m³, taken from OpenWeather's published breakpoints. Confirm them against the current docs. OpenWeather's AQI is the worst level across all pollutants, so an AQI derived from PM2.5 alone is only an approximation.

Jobs, schedules and sensors

  • daily_ingest (all ingest, transform and marts assets). Started by kaggle_update_sensor. A fallback schedule at 06:00 UTC catches days when the sensor misses the update.
  • daily_ml (features → forecasts → accuracy → alerts). Started by an asset sensor when fct_observation finishes.
  • weekly_retrain (pm25_model). Cron on Sundays. Promotes the new model only if the promotion rule in section 06 passes.
  • ops_recorder. A run_status_sensor plus an asset-check hook that write to ops.* whenever a run starts, succeeds or fails. This is what the dashboard reads.
  • Freshness. A freshness policy on fct_observation and pm25_forecasts (26 hours). A late day shows up as stale in Dagster and on the dashboard.

Resources

PostgresResource, KaggleResource, OpenWeatherResource, DbtCliResource, MlflowResource and ApnsResource. All of them are configured from environment variables, so local and deployed runs use the same code.

06

ML forecasting

Avoid target leakage

AQI is calculated from the pollutant concentrations. A model that predicts AQI from same-time pm2_5, pm10 or o3 will score close to 100% and learn nothing. The dataset's target_* columns and every same-time pollutant are dropped from the features. The model predicts the next reading only from information available now.

Problem

  • Target: PM2.5 at the city's next reading about 24 hours ahead (horizon_h = 24). In phase 1 there is one snapshot per day, so this is "the next snapshot", not a daily average. Once hourly collection runs, it becomes the daily mean for D+1, then D+2 and D+3.
  • Outputs: median PM2.5, a p10–p90 interval, and an AQI class derived from the PM2.5 breakpoints.

Features

  • PM2.5 history: lags 1–7, rolling mean over 3 and 7 readings, rolling standard deviation over 7.
  • Weather observed at as_of: temperature, humidity, pressure, wind speed, wind direction as sin and cos, gusts, clouds, rain, snow. Low wind and high pressure tend to trap pollution.
  • Calendar: day of week, weekend flag, month as sin and cos.
  • Location: lat, lon, continent, log population, and city_key as a LightGBM categorical feature.
  • Phase 2: OpenWeather's weather forecast for the target time. Tomorrow's wind matters more than today's.

Models

ModelRole
Persistence (tomorrow equals today)Baseline 1. Hard to beat for air quality, which makes it the bar every model must clear.
7-day city meanBaseline 2
LightGBM on log1p(pm25)Main model (median)
LightGBM quantile, α = 0.1 and 0.9Prediction interval for the apps' "likely range"

Validation

  • Rolling-origin backtest: an expanding training window with 4 test folds of 14 days each. Never split randomly.
  • Metrics: MAE and RMSE on PM2.5, AQI class accuracy and macro F1, and interval coverage (target about 80%).
  • Report results by continent and by AQI band. A model that does well on clean cities but badly on polluted ones is not useful to the people who need the forecast most.

Tracking and promotion

  • MLflow with a Postgres backend stores parameters, metrics, feature importance and the model file. The registry aliases are champion and challenger.
  • Promotion rule: the challenger's MAE on the last fold is at most 98% of the champion's, it beats persistence, and interval coverage is between 70% and 90%. Otherwise the champion stays and the run is logged as rejected.
  • Monitoring: forecast_accuracy compares each forecast with what actually happened. PSI drift on the top features and the missing-data rate are both shown on the web dashboard's Model page.

The two apps

Each app is its own UI/UX case study for a different user. The web dashboard is dense and built for diagnosis. The iOS app is calm and answers one question: is the air OK today and tomorrow?

TomorrowMVP

Forecast AQI with a "likely range" bar taken from p10–p90, and a plain-language sentence like "Similar to today".

Three screens: what AQI means, why location is asked for, and setting up alerts. Each can be skipped.

Push notification when tomorrow's forecast for a saved city reaches your threshold. At most one per city per day.

WidgetsLater

Small widget with AQI and city. Medium widget adds tomorrow's forecast. Lock-screen widget.

Tips for each AQI level for sensitive groups (asthma, children, outdoor exercise), written plainly.

OfflineLater

Last data is cached and shown with its age, plus an offline banner.

Design the honest version

In phase 1 each city has one reading per day, and some cities will be missing on some days. Both apps should always show how old the data is and say clearly when a city has no recent reading, rather than showing an old number as if it were current. Both apps must also show the OpenWeather and dataset attribution (CC BY 4.0).

10

Roadmap

About 13 weeks part-time. UI/UX design for each app can start while the backend phases before it are still being built.

Week 1

Phase 0: Setup

Repo, Compose stack, Kaggle token, first manual download, and a notebook to profile the data: history length, nulls, units, cities per day.

Done when: the data profile is written up and the open questions in section 11 are answered.

Weeks 2–3

Phase 1: Ingestion and warehouse

Raw assets, the Kaggle sensor, dbt staging, core and marts, and asset checks.

Done when: a new Kaggle version lands in the marts automatically, and a broken file fails a check.

Week 4

Phase 2: Ops metadata and API

The ops recorder sensor, ops.* tables, FastAPI read endpoints, the OpenAPI spec and generated clients.

Done when: /v1/ops/summary and /v1/cities/* return live data.

Weeks 5–6

Phase 3: Forecast model

Feature asset, baselines, LightGBM with quantile models, backtests, MLflow, the promotion rule, and the daily forecast and accuracy assets.

Done when: the champion model beats persistence in the backtest and forecasts are served by the API.

Weeks 5–9

Phase 4: Web dashboard

Research and wireframes (weeks 5–6), then a hi-fi design and a small design system, then the MVP pages.

Done when: someone else can diagnose a failed run using only the dashboard.

Weeks 8–12

Phase 5: iOS app

User interviews (3–5 people), flows, hi-fi design, then the SwiftUI MVP, then alerts and widgets.

Done when: the app is on TestFlight with the MVP features, and alerts fire from the daily forecast.

Week 13

Phase 6: Hardening and write-up

Hourly OpenWeather collection (if the call limits allow), deploy, README, architecture diagrams, and a case study for each app.

Done when: the public demo links and case studies are live.
